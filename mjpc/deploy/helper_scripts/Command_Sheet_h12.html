The base state on rt/sportmodestate stands in for Unitree's closed-firmware estimator (off in debug mode). The node runs unmodified — it cannot tell whether that state came from the twin's truth, our filter (B1), or OptiTrack mocap (B2). Exactly one publisher writes that topic at a time — B1 = the laptop estimator, B2 = the Motive PC. Run both and the two writers fight.

Forward lean — solved

rev 2026-06-14

Root cause: the IMU pitch zero-offset (−1.6°), found by checking calibration with the body verified vertical — not the CoM and not the ankle. One constant, corrected in-node by default (+1.6°). --gravity_ff 0.85 is now standard to calm the residual fore-aft swing.

B — Hardware: estimator vs OptiTrack, head-to-head

▶ NEXT ROBOT

Run the same stand (Lean H12 Magpie, strategy 6) twice. The node, safety layer, gains, the baked-in IMU calib (+1.6°), --twin_dt 0.001 and --gravity_ff 0.85 are identical both runs — the only difference is who publishes rt/sportmodestate: our laptop estimator (B1) or the OptiTrack mocap on the Motive PC (B2).

One publisher per topic. B1 and B2 both write rt/sportmodestate — never run the estimator (publishing it) and publish_sportmodestate.py at the same time, or two writers fight and the base state is garbage. What changes between phases — everything else is identical
The constant core of every node launch:
h12_control_node --task "Lean H12 Magpie" --strategy 6 --use_twin_time --plan_threads 12 --latency_comp --policy_blend_sec 4.5
…then exactly one phase delta (the amber slot):
A1 → --imu_pitch_offset_deg 0 A2 → + --sportstate_topic …_est B1 → --gravity_ff 0.85 · --twin_dt 0.001 · estimator publishes B2 → same node · OptiTrack publishes rt/sportmodestate

A2 twin UNPLUGGED estimator → …_est (node reads …_est) --sportstate_topic …_est · --imu_pitch_offset_deg 0 default_safety_full.yaml
B1 robot wired enx estimator (laptop RW-EKF) --twin_dt 0.001 · --gravity_ff 0.85 · (imu +1.6 baked in) default_safety_full + estop_node
B2 robot wired enx + Motive PC OptiTrack mocap (Motive PC) · est → …_est --compare = ruler (same node as B1) default_safety_full + estop_node
  • · Never --iface lo — loopback disables multicast, DDS goes deaf. Twin = --no-auto-iface.
  • · --imu_pitch_offset_deg defaults to 1.6 = the ROBOT's measured IMU pitch zero-offset. The TWIN has no mount offset → pass 0 on A1/A2, else the twin leans. (_twin_probe is unaffected — different code path.)
  • · Twin tests with the dongle plugged would auto-pin the robot NIC and miss the twin — unplug first.
  • · Falls at ~40–90 s with slow knee-creep then ankle-torque blowup = the known cost-side sink / strut, NOT a pipeline failure.
  • · default_safety_full's state estop is LATCHING: a fall / transient (q / dq / tau out of range) drives the relay to zeros for good — restart the safety node to clear and rerun. A trip ends that run; it is not a pipeline failure.
  • · B2 only: exactly ONE writer on rt/sportmodestate. Run OptiTrack or the estimator-publishing-it — never both. In B2 the estimator must go to rt/sportmodestate_est --compare (a ruler), not the live topic.
  • · magpie: task is "Lean H12 Magpie" and the twin runs --magpie. Grippers are welded mass-only (nu=27, nq unchanged) → no cost/weight/gain retune; swap back to "Lean H12" (no --magpie) when they come off. Validate the OptiTrack AXIS_MAP once with the +x / +z motion test before trusting B2.
